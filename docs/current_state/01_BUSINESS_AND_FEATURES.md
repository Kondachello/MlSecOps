## 1. Что это за продукт

**MLSecOps Platform** — это «контур безопасности» поверх обычного MLOps-процесса. Идея:
на каждом шаге жизни ML-модели (данные → код → обучение → артефакт → реестр → деплой →
прод-инференс) стоит **автоматическая проверка безопасности (Security Gate)**. Прошёл —
едешь дальше; не прошёл — блок, и причина видна. Плюс **всё пишется в неподделываемую историю
(Audit Trail)**, а критичные модели требуют **ручного одобрения человеком (HITL)**.

Бизнес-ценность (из `docs/PRD.md`): ML приносит деньги, пока не ломается. MLOps делает систему
надёжной и воспроизводимой; **MLSecOps делает её неуязвимой** — ловит отравленные данные,
секреты в коде, вредоносные веса (pickle-RCE), подделку артефактов, кражу модели через API,
дрейф и т.д. Безопасность — встроенная фича платформы, а не патч поверх инцидентов.

Проект исторически делили на трёх разработчиков:
- **A** — ядро: БД, хранилище, авторизация, центральный бэкенд (Gatekeeper), MLflow-интеграция.
- **B** — сами проверки (гейты G1–G5) и CI/CD-конвейер.
- **C** — 3 ML-модели, рантайм-защита API (G7), мониторинг (G6) и веб-интерфейс (UI).

**Текущая кодовая база — это слитая система:** реализованное ядро A + гейты B + объединённый
веб-интерфейс (полированный UI «C», подключённый к реальному бэкенду A). См. историю слияния
в `docs/current_state/03_FRONTEND_TECHNICAL.md` и в памяти проекта.

## 2. Роли и пользователи (RBAC)

В системе пять ролей. Роль НЕ выдаётся при саморегистрации — её назначает только **MLSecOps**
(администратор безопасности). До назначения роли пользователь может войти, но привилегированных
действий не имеет.

| Роль | Кто это | Что делает в системе | Клиренс |
|---|---|---|---|
| **DS** (Data Scientist) | разработчик моделей | экспериментирует в MLflow, гоняет security check своих артефактов, шарит результаты, запускает гейты | 1 |
| **DE** (Data Engineer) | инженер данных | загрузка/версионирование датасетов, выдача данных | 1 |
| **Product** | продакт/стейкхолдер | смотрит реестр, паспорта, дашборд (read-oriented) | 2 |
| **MLSecOps** | админ безопасности | выдаёт роли/доступы, делает HITL-Approve, ведёт триаж находок, видит всё | 3 |
| **CEO** | топ-менеджмент | read-only дашборд «всё ли под контролем», карта покрытия | 4 |

**Клиренс (clearance)** — числовой уровень доступа роли. Используется для контролируемого
шаринга артефактов по принципу **read-down**: старшая роль видит то, что расшарила младшая
(MLSecOps/CEO видят расшаренное DS), но не наоборот. Подробнее — §4.4.

**Принципы идентичности (зафиксированы):**
- Один аккаунт на наш сервис и на MLflow (единый JWT).
- **Личность неподделываема:** при работе с MLflow личность пользователя проставляет сервер
  (auth-прокси), клиент её задать не может.
- Роль для проверки прав берётся **из БД** (а не из токена) — отзыв роли действует мгновенно.

## 3. Жизненный цикл ML-актива и Security Gates (концепция)

```
ДАННЫЕ ─[G1]→ КОД ─[G2][G3]→ ОБУЧЕНИЕ(в CI) ─→ АРТЕФАКТ ─[G4]→ РЕЕСТР ─[G5]→
                                                                  │ (HITL для Tier=HIGH)
                                                                  ▼
                                                       ДЕПЛОЙ → ПРОД-API ─[G7 рантайм]
                                                                  │
                                                        [G6 мониторинг 24/7]
```

| Gate | Что охраняет | Закрывает угрозы | Статус в текущей системе |
|---|---|---|---|
| **G0** Onboarding | паспорт модели (ModelCard), авто-Tier | Shadow AI | 🟡 есть модель/валидатор `core/model_card.py`, не подключён к ручке |
| **G1** Data | данные: схема, баланс классов (отрава), PII, инъекции | #1 #2 #11 #15 | ✅ запускается по кнопке (`/ci/trigger` data_gate) |
| **G2** Code | код: секреты (gitleaks), CVE (pip-audit), SAST (bandit) | #8 #10 | ✅ запускается по кнопке (`/ci/trigger` code_gate) |
| **G3** Supply | зависимости: typosquatting, пиннинг, источник | #9 #3 | ✅ запускается по кнопке (`/ci/trigger` dependency_gate) |
| **G4** Model | файл модели: формат (анти-pickle), скан весов, SHA, подпись | #3 #4 #26 | 🟡 код гейта есть (`src/gates/model_gate`), кнопкой не подключён; в security check — плейсхолдер |
| **G5** Registry | паспорт + lineage + Tier перед реестром | #20 #23 | 🟡 код гейта есть (`src/gates/registry_gate`), реестр в БД — заглушка |
| **G6** Observability | прод: дрейф (PSI), подмена модели | #14 #4 | 🚧 код мониторинга в репо, в бэкенд/дашборд не прокинут |
| **G7** Runtime | прод-API: кража модели, DoS, утечки | #5 #6 #11 #12 #13 | 🚧 код serve в репо, как сервис в текущем стенде не поднимается |

**Ключевой принцип гейта:** единый контракт — программа получает артефакт, печатает JSON-отчёт
(`{gate, passed, checks:[{check,status,severity,detail,evidence}], failed_checks}`) и возвращает
exit 0 (PASS) / 1 (FAIL). Поэтому гейт зовётся одинаково и в CI, и из бэкенда, и в Docker.
`evidence` («улика») — это то, что UI показывает как «причину».

## 4. Реализованный функционал (по фичам)

### 4.1 Аутентификация и онбординг ✅

- **Саморегистрация** (`/auth/register`): любой может создать аккаунт (логин/пароль/email).
  Создаётся пользователь **без роли** — сразу ничего привилегированного.
- **Логин** (`/auth/login`): по паролю → выдаётся короткоживущий **JWT** (по умолчанию 8 часов).
  Один и тот же JWT действителен и для нашего API, и (через прокси) для MLflow.
- **Кто я** (`/auth/me`): личность + актуальные роли из БД.
- **Назначение роли**: только MLSecOps через админку. До этого — «ожидайте назначения роли».
- **Bootstrap первого админа**: скрипт `infra/seed_admin.py` создаёт `msecops`/`admin-pass`
  с ролью MLSecOps (идемпотентно), чтобы было кому выдавать роли.

Бизнес-смысл: контролируемый онбординг — никто не получает прав «по умолчанию», least privilege.

### 4.2 Личный кабинет разработчика ✅

- Показывает имя, роли, клиренс.
- **«Получить MLflow-токен»** (`/auth/token`): выдаёт персональный токен и готовый
  Python-сниппет для Jupyter/ноутбука (`MLFLOW_TRACKING_URI` + `MLFLOW_TRACKING_TOKEN`).
  С этим токеном разработчик логирует эксперименты в MLflow из своего ноутбука.
- Показывает **последние MLflow-раны** (что разработчики залогировали).

### 4.3 Изоляция работы в MLflow + приватность по умолчанию ✅

Это одна из центральных фич платформы.

- Каждый разработчик работает в **своём MLflow-эксперименте = «аккаунт»**.
- Всё, что он логирует (раны = «сессии разработки»: данные + код + модель в одном ноутбуке),
  по умолчанию **приватно** — видно только ему.
- **Личность владельца неподделываема:** при создании рана/эксперимента auth-прокси штампует
  серверный тег `mlsecops.owner = <логин из токена>` и фиксирует владение в БД. Клиент не может
  выдать себя за другого.
- **Фильтрация видимости работает на двух уровнях:**
  1. В нашем UI (раздел «Мои артефакты») — показываются только свои + расшаренные.
  2. В самом MLflow (через прокси) — при поиске/чтении ранов и экспериментов чужое приватное
     вырезается из ответа, прямой запрос чужого приватного рана → `403`.

Бизнес-смысл: закрывает «утечку/кражу наработок между командами» и «попадание непроверенного
артефакта в общий доступ».

### 4.4 Security check + контролируемый шаринг артефактов 🟡 / ✅

Поток (полностью рабочий, логика проверки — плейсхолдер):
1. Разработчик в «Мои артефакты» видит свои раны (сессии).
2. Жмёт **«Запустить security check»** (`/artifacts/{run_id}/check`). Только владелец.
   Сейчас проверка — **плейсхолдер** (4 «как будто»-проверки: формат весов, скан секретов,
   PII-маркеры, lineage — все возвращают PASS + дебаг-вывод в консоль). Реальные гейты подключатся
   позже; контракт результата уже стабильный (пишется в БД и в Audit Trail).
3. После успешной проверки активируется **«Поделиться»** (`/artifacts/{run_id}/share`):
   - без указания ролей → шаринг **по клиренсу** владельца (read-down: видят роли с clearance ≥ уровня);
   - с указанием ролей → **кастомный allow-list** ролей (переопределяет клиренс).
4. **«Снять шаринг»** (`/artifacts/{run_id}/unshare`) — снова приватно.
5. Каждое действие пишется в Audit Trail (`artifact_security_check` / `artifact_shared` / `artifact_unshared`).

Гарантия: артефакт не станет видимым другим, пока владелец **явно** не прогонит проверку и не
нажмёт «Поделиться». Видимость ограничена клиренсом (least privilege) либо явным списком ролей.

### 4.5 Audit Trail — неподделываемая история ✅

- **Единственная точка записи** — `log_event()`. Любое значимое действие (логин, выдача роли,
  доступ, шаринг, отказ доступа, bootstrap и т.д.) фиксируется.
- **Hash-chain:** `row_hash = sha256(prev_hash + канонизированное_тело_события)`, генезис = `0×64`.
  Подделка/удаление любой строки рвёт цепочку.
- **Проверка целостности** (`/events/verify_chain`): пройти все события, пересчитать хэши,
  найти разрыв → `{ok, broken_at, count}`. В UI — кнопка «Проверить цепочку хешей».
- Актор события — **серверная личность** (из токена), не клиентское поле.
- В Postgres-режиме у роли приложения отзываются UPDATE/DELETE на `events` (append-only).

Бизнес-смысл: «никто не забыт, ничего не упущено»; целостность журнала (угроза #24).

### 4.6 Запуск Security-гейтов по кнопке ✅

Раздел «Инструменты»: запуск отдельных гейтов на реальных артефактах через `/ci/trigger`:
- **G1 Data Gate** — на выбранном CSV (схема, PII, баланс классов).
- **G2 Code Gate** — на коде репозитория (секреты, SAST, CVE).
- **G3 Dependency Gate** — на зависимостях (allow-list, пиннинг).

Два режима (автоматически):
- **GitHub Actions** — если заданы `GITHUB_TOKEN`/`GITHUB_REPO`: триггерит workflow через
  `repository_dispatch` (отдаёт ссылку на Actions).
- **Локально** — иначе: гейт выполняется in-process, отчёт (PASS/FAIL по каждой проверке +
  detail) показывается прямо в UI.

Плюс **загрузка CSV** на сервер (`/upload`) и список доступных файлов (`/files`).

### 4.7 Администрирование (MLSecOps) ✅

Раздел «Пользователи»:
- список пользователей с ролями;
- **создать пользователя** (+ опц. роль);
- **назначить роль** существующему;
- **выдать доступ к датасету** (с флагом `can_export` для контроля экспорта данных).

Все действия — с записью в Audit Trail.

### 4.8 Реестр моделей (чтение) ✅ (данные пусты)

Раздел «Реестр» читает зарегистрированные модели из **MLflow Model Registry** (`/models`).
Сейчас реестр пуст (моделей ещё не регистрировали) → показывается честная пустая заглушка.
Полноценный реестр в нашей БД (с Tier, lineage, статусами, паспортом) — пока 🚧.

### 4.9 GRC: Карта покрытия и Контур ✅

- **Карта покрытия** — каталог из **30 контролей безопасности** (`src/common/controls.py`):
  каждая угроза → контроль → гейт/слой → конкретные тесты → стандарты (MITRE ATLAS, OWASP ML,
  NIST AI RMF, ФСТЭК). Статусы: `live` (реализовано+тест), `planned` (зона инфраструктуры/A),
  `accepted` (остаточный риск принят через RiskAcceptance). Текущее покрытие: **25/30 live (83%)**.
  MLSecOps может «принять остаточный риск» (RiskAcceptance) с обоснованием.
- **Контур** — сводный обзор рантайм-защит периметра и состояния (число открытых находок —
  из реального бэка).

Бизнес-смысл: замкнутый GRC-контур — доказуемое покрытие угроз контролями и тестами; отчёт
для CEO «сколько контролей закрыто».

## 6. Сквозные сценарии, которые РАБОТАЮТ сейчас

**Сценарий A. Онбординг и роли**
1. Пользователь регистрируется (UI → «Регистрация»).
2. MLSecOps (`msecops`/`admin-pass`) в «Пользователи» назначает ему роль DS.
3. После релогина у пользователя появляются разделы DS.

**Сценарий B. Разработчик: от ноутбука до контролируемого шаринга**
1. DS в «Кабинет» жмёт «Получить MLflow-токен», копирует сниппет в ноутбук.
2. Логирует эксперименты в MLflow через прокси (например, `examples/dev_train_mock.py` —
   реальное обучение sklearn на `load_breast_cancer`, 4 сессии).
3. Раны приватно появляются в «Мои артефакты».
4. Жмёт «Запустить security check» → PASS (плейсхолдер).
5. «Поделиться» (по клиренсу или выбрав роли) → ран становится виден нужным ролям.

**Сценарий C. Приватность/изоляция**
1. Второй DS НЕ видит чужие приватные раны — ни в «Мои артефакты», ни в самом MLflow
   (прокси режет выдачу; прямой запрос чужого рана → 403).
2. После шаринга нужные роли видят ран; «Снять шаринг» снова скрывает.

**Сценарий D. MLSecOps: безопасность**
1. Запуск гейтов по кнопке (Data/Code/Dependency) на реальных файлах/коде → видит PASS/FAIL + причину.
2. История событий + «Проверить цепочку хешей» (целостность).
3. Карта покрытия: 83% контролей live; принятие остаточного риска.

**Сценарий E. CEO**
- Read-only дашборд: модели/события/находки/целостность аудита; карта покрытия с процентом.

## 8. Ограничения и важные оговорки

- **Security check — плейсхолдер** (всегда PASS). Поток шаринга реален, но реальной блокировки
  по содержимому артефакта пока нет.
- **Реестр пуст** — нет ручки регистрации моделей в нашу БД; «Реестр»/«Паспорт»/«Деплой»
  показывают честные заглушки.
- **Рантайм (G6/G7) и MinIO** в текущем локальном стенде не поднимаются — это код «C»/инфра,
  не входившие в слияние фронта.
- **Fail-open для нетрекаемых экспериментов:** эксперименты без записи владения (legacy/Default
  в MLflow) прокси НЕ прячет — задокументированный компромисс.
- **Не фильтруются artifact-эндпоинты MLflow** (скачивание весов) — изоляция опирается на штамп
  владельца, но скачивание не режется.
- **Postgres-режим** новые таблицы (`experiment_owner`, `artifact_acl`) поддерживает (в `init.sql`),
  но в основном гоняли на SQLite-деве.

## 9. Как запустить (для проверки бизнес-сценариев)

```
.\infra\stop.cmd       # если что-то висит с прошлого раза
.\infra\start.cmd      # MLflow :5000, backend :8200, UI :8501
```
- UI: http://localhost:8501 — логин `msecops` / `admin-pass`.
- API (Swagger): http://localhost:8200/docs
- MLflow: http://localhost:5000

> Локальный порт бэка — **8200**, не 8000 (на Windows 8000 попадает в зарезервированный
> Hyper-V/winnat диапазон). Подробности — `02_BACKEND_TECHNICAL.md` §«Запуск и порты».
