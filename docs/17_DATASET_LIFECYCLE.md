# 17 — Жизненный цикл датасета

## 17.1 Источники данных

| Источник (`source_type`) | Пример | Доверие |
|---|---|---|
| `local` / `internet` | скачан с интернета/HF/Kaggle, локальный файл | **низкое** — «дикие» данные |
| `corp_storage` | внутренний корпоративный источник, ещё без ИБ-подписи | среднее, но **проверяется полностью** |
| `verified_id` | ранее проверенный нашей платформой (есть в `verified_datasets`) | высокое (fast-path по хэшу) |

## 17.2 Принцип проверки (КАНОН)

**Внутренние данные проверяются полностью, всеми применимыми проверками** — никакого
«облегчённого режима» по признаку «источник доверенный». Причина: у нас может быть инсайдер,
который внедряет закладки. Все данные равны перед G1.

Единственное законное ускорение — **fast-path по хэшу**: если SHA-256 загружаемого датасета
**бит-в-бит совпадает** с записью в `verified_datasets`, повторная полная проверка не нужна
(это буквально тот же файл). Любое изменение → новый хэш → **полная проверка с нуля**.

> Это сознательно отличается от ранних черновиков, где для `corp_storage` предлагалось
> пропускать вирус-скан. Отвергнуто: инсайдерская угроза важнее экономии.

## 17.3 Функции (что умеет система с датасетом)

1. Зарегистрировать сущность-датасет (паспорт, owner, source_type, версия).
2. Загрузить файл.
3. Загрузить обновление датасета (новая версия → **G1 с нуля**).
4. Скачать (по праву доступа; экспорт — по `data_export`).
5. Загрузить с HF/Kaggle по ссылке.
6. Передать данные между сотрудниками безопасно (frontender → DS через сервис, с контролем доступа).

## 17.4 Состояния и переходы

```
[загрузка] → registered → G1 → PASS → available  (+ запись в verified_datasets, хэш)
                              └ FAIL → quarantine (+ finding, не удаляем)
available → (привязан к прод-модели) → prod_locked  (неизменяем)
```

## 17.5 Неизменяемость под продом и обновления

- Датасет, на котором обучена **прод-модель**, переходит в `prod_locked` и **не принимает
  обновления** (наравне с неизменяемостью прод-артефакта).
- Чтобы доработать модель на «новых» данных: делаем **копию датасета** (новая версия) → она
  проходит **полную G1** → на ней обучается новая модель в CI → полный конвейер → **blue-green
  замена** прод-модели (см. [`05_CANONICAL_FLOW.md`](05_CANONICAL_FLOW.md) §5.6).
- Старые версии датасета не удаляются (lineage/аудит/откат).

## 17.6 Ретроактивная инвалидация (связь с моделями)

Если ранее проверенный датасет позже признан небезопасным:
- по `model_versions` (lineage) находим все модели, обученные на нём;
- помечаем их кандидатами на пересмотр; если такая модель в проде — инцидент + решение MLSecOps
  об откате/retire.

## 17.7 Версионирование в MLflow (для DS)

DS в скрипте обучения фиксирует версию данных встроенным механизмом:
```python
import mlflow, mlflow.data, pandas as pd
df = pd.read_parquet("data.parquet")
ds = mlflow.data.from_pandas(df, source="<path_or_id>", name="training_dataset")  # считает SHA-256 + профиль
with mlflow.start_run():
    mlflow.log_input(ds, context="training")   # привязка данных к ране модели
    # ... обучение, mlflow.log_model(...)
    mlflow.set_tags({                            # ИБ-теги (личность проставляет сервер/прокси, не клиент)
        "security.git_commit": "<sha>",
        "security.data_source_type": "local|internet|corp_storage|verified_id",
        "security.data_path_or_id": "<...>",
    })
```
Бэкенд через `mlflow.client.search_runs()` собирает выпадашку (модель/run/датасет/хэш) для формы
верификации (см. [`11_BACKEND_API.md`](11_BACKEND_API.md)).
