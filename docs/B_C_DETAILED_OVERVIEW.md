> **впервые видит проект**. Если встретится незнакомый термин — он есть в [`02_GLOSSARY.md`](02_GLOSSARY.md).

## Часть 0. О чём вообще проект (на одной странице)

Компания обучает и эксплуатирует ML-модели (например, кредитный скоринг). Модели приносят
деньги — но могут стать дырой в безопасности: кто-то подсунет «отравленные» данные, оставит
секрет в коде, притащит модель с вирусом внутри весов, или начнёт воровать модель через API.

**Платформа MLSecOps** — это «контур безопасности» поверх обычного ML-процесса. Идея простая:
**на каждом шаге жизни модели стоит автоматическая проверка (Gate). Прошёл — едешь дальше.
Не прошёл — блок, и причина видна.** Плюс всё записывается в неподделываемую историю, а
критичные модели требуют ручного одобрения человеком (HITL).

Работу поделили на трёх разработчиков:
- **A** — «ядро»: база данных, хранилище, авторизация, центральный бэкенд (ещё в работе).
- **B** — **сами проверки (гейты) и CI/CD-конвейер**.
- **C** — **ML-модели, защита их API в реальном времени, мониторинг и веб-интерфейс**.

Ниже — детально, что сделали **B и C**, и как это всё стыкуется.

## Часть 1. Большая картина: как устроена защита

Жизнь модели проходит «слева направо» через стадии. На стадиях стоят гейты `G0…G7`:

```
ДАННЫЕ ──► [G1] ──► КОД ──► [G2][G3] ──► ОБУЧЕНИЕ(в CI) ──► АРТЕФАКТ ──► [G4] ──► РЕЕСТР ──► [G5]
                                                                                        │
                                                                       (HITL для HIGH)  ▼
                                                              ДЕПЛОЙ ──► ПРОД-API ──► [G7 runtime]
                                                                                        │
                                                                              [G6 мониторинг 24/7]
```

| Gate | Что охраняет | Чей |
|---|---|---|
| G1 Data | данные (отрава, ПДн) | **B** |
| G2 Code | код (секреты, уязвимости) | **B** |
| G3 Supply | зависимости (поддельные/непиненные пакеты) | **B** |
| G4 Model | артефакт модели (опасный формат, подмена, подпись) | **B** |
| G5 Registry | паспорт и связность (lineage) перед попаданием в реестр | **B** |
| G6 Observability | прод: дрейф данных, подмена модели | **C** |
| G7 Runtime | прод-API: кража модели, DoS, утечки | **C** |

Главный принцип: **у каждого гейта одинаковый «разъём» (контракт)**. Любой гейт — это программа,
которая получает на вход артефакт, печатает JSON-отчёт и возвращает код `0` (PASS) или `1` (FAIL).
Поэтому гейты можно запускать одинаково — и вручную, и в CI, и в Docker.

## Часть 2. Работа разработчика B — Security Gates и CI/CD

### 2.1 Единый контракт гейта (фундамент всего)

Каждый гейт лежит в своей папке `src/gates/<имя>/` и предоставляет три функции:

```python
def gate_check(target, ...) -> list[dict]:
    # список результатов проверок; каждый:
    # {"check": "имя", "status": "PASS"|"FAIL"|"SKIP", "severity": "...", "detail": "...", "evidence": {...}}

def build_report(target, results) -> dict:
    # сводка: {"gate":"G1", "asset":"...", "passed": True/False, "checks":[...], "failed_checks":[...]}

def main():
    # разбор аргументов, печать JSON-отчёта, exit(0) если passed иначе exit(1)
```

Три важных правила (зачем — объяснено):
1. **Гейт сам в базу данных НЕ пишет.** Он только печатает отчёт. Запись в историю (`findings`,
   `events`) делает «оркестратор» (бэкенд A). Почему: чтобы гейт можно было запустить в CI, где
   базы нет, и он не падал.
2. **Graceful degradation:** если нужный инструмент не установлен — проверка возвращает `SKIP`
   (а не падает). Например, нет `gitleaks` → секрет-проверка `SKIP`, остальные идут дальше.
3. **`SKIP` ≠ `PASS` и ≠ `FAIL`.** Это «не смогли проверить». Видно честно.

`evidence` — это «улика»: что именно нашли (какая строка, какой пакет, какой хэш). Именно его
потом показывает UI в разделе «Находки» под кнопкой «Показать причину».

### 2.2 Изоляция: один гейт = один Docker-образ

У каждого гейта свой `Dockerfile` и свой `requirements.txt`. Зачем:
- **Безопасность:** опасный артефакт (например, модель с вирусом) сканируется в одноразовом
  контейнере с `--network none`, а не на основной машине.
- **Чистота инструментов:** у `code_gate` свои сканеры (gitleaks, trivy), у `data_gate` — только
  pandas. Версии не конфликтуют.

Запускается одинаково:
```bash
docker run --rm --network none -v "$ARTIFACT:/in:ro" mlsec-gate-data --path /in --json
```
Сборка всех образов — `infra/docker-compose.gates.yml` (`make build-gates`).

### 2.3 Гейты по отдельности — что именно проверяют

#### G1 — Data Gate (`src/gates/data_gate/data_gate.py`)
Стоит на **загрузке датасета**, до обучения. Защищает от «грязных» и опасных данных.
Проверки:
- **format_readable** — файл вообще читается (CSV/Parquet).
- **schema** — набор колонок совпадает с эталоном (нет лишних/недостающих).
- **class_balance** — анти-«отравление»: если доля класса резко перекошена (меньшинство вдруг
  стало >30%) — подозрение на Data Poisoning. *Пример: было 2% мошенников, стало 50% → FAIL.*
- **типы/диапазоны, пропуски, дубликаты, константы** — качество данных.
- **pii** — поиск персональных данных регулярками (email, номера карт) → нашли → FAIL.
- **prompt_injection** — для текстовых данных ищет фразы вроде «ignore previous instructions».

Закрывает угрозы: **#1 Data Poisoning, #2 утечка ПДн, #11, #15.**

#### G2 — Code Gate (`src/gates/code_gate/code_gate.py`)
Стоит в **CI на код**. Два режима: `--stage ci` и `--stage deploy`.
Проверки (каждая вызывает внешний сканер; нет сканера → SKIP):
- **secrets** — `gitleaks`: пароли/API-ключи в коде → FAIL.
- **sast** — `bandit`: опасные паттерны кода; **FAIL только при HIGH-severity** (чтобы не шуметь).
- **cve_deps** — `pip-audit`: известные уязвимости (CVE) в зависимостях → FAIL при CRITICAL/HIGH.
- **trivy_image** — только на `deploy`: сканирует собранный Docker-образ. **trivy запускается
  ровно один раз** — на деплое (а не на каждом шаге).

Код умеет **разбирать JSON-вывод** сканеров (функции `_parse_gitleaks/_parse_bandit/...`), а не
просто смотреть на код возврата — поэтому в `evidence` попадает конкретная строка/правило.
В `Dockerfile` ставятся `gitleaks 8.18.4` и `trivy 0.52.2`.
Закрывает: **#8 CVE в библиотеках, #10 секреты в коде.**

#### G3 — Supply Gate (`src/gates/dependency_gate/dependency_gate.py`)
Цепочка поставки зависимостей. Граница с G2: *уязвимости (CVE) — это G2; имена/версии/источник —
это G3.* Проверки:
- **name_allowlist** — анти-typosquatting: каждый пакет сверяется с белым списком. Поддельные
  двойники (`pytirch`, `tenserflew`) → FAIL.
- **version_pinning** — версии должны быть зафиксированы (`==`/lock), иначе FAIL.
- **trusted_source** — источник пакетов (`--index-url`/namespace HuggingFace) из доверенного списка.

Закрывает: **#9 Typosquatting, #3 (источник).**

#### G4 — Model Gate (`src/gates/model_gate/model_gate.py`)
Самый «ИБ-шный» гейт — проверяет **сам файл модели**. Проверки:
- **weights_format** — белый список безопасных форматов: разрешены `.safetensors/.onnx/.cbm/.txt`,
  **запрещены `.pkl/.joblib/.pt/...`**. Почему: pickle-формат **исполняет код при загрузке** —
  классический способ спрятать вирус в «модели». *Важно: гейт НЕ открывает .pkl для проверки —
  только смотрит расширение/сигнатуру.*
- **weights_scan** — `modelscan`/`picklescan`: ищет вредоносные опкоды в весах.
- **integrity_sha256** — считает SHA-256 файла и сверяет с эталоном из реестра. Не совпало →
  значит файл **подменили** → FAIL.
- **signature_cosign** — проверка криптоподписи (`cosign`). На деплое можно требовать обязательно
  (`--require-signature`).
- **consistency** — тест «обучение↔инференс» (через `--consistency-script`), см. часть C.

Закрывает: **#3 pickle/RCE, #4 подмена артефакта, #19 skew, #26 подпись.** `Dockerfile` ставит `cosign 2.2.4`.

#### G5 — Registry/Compliance Gate (`src/gates/registry_gate/registry_gate.py`)
Стоит **перед записью модели в реестр**. Проверяет «документированность и связность»:
- **card_completeness** — у модели есть паспорт со всеми полями (owner, Tier, источник, назначение…).
- **tier_validity** — `Tier ∈ {LOW, MED, HIGH}` + авто-правила: если источник внешний / данные из
  интернета / модель обучена НЕ в CI → Tier обязан быть `HIGH` (принцип «подозревай худшее»).
- **sha256_format** — хэш артефакта валиден (64 hex-символа).
- **lineage** — есть связка «данные↔код↔модель»: `dataset_version + git_sha + sha256`. Без неё —
  это «модель из ниоткуда» (Shadow AI) → FAIL.
- **version_unique** — уникальность версии (проверяет оркестратор, тут `SKIP`).

Закрывает: **#20 Shadow AI, #23 версионирование/lineage.** Отчёт включает `severity_summary` —
сводку по серьёзности.

### 2.4 Демо-«приманки» (фикстуры) — чтобы показать срабатывание
Всё «плохое» лежит **только в `demo/`** (никаких реальных секретов/вирусов):
- `demo/insecure/leaky.py` — поддельный «секрет» (ловит gitleaks) + `subprocess(shell=True)`
  (ловит bandit как HIGH).
- `demo/insecure/requirements.txt` — старые пакеты с CVE (ловит pip-audit).
- `demo/insecure/requirements_vuln.txt` — `pytirch`/`tenserflew` (ловит G3).
- `demo/insecure/model_card_incomplete.json` — неполный паспорт (ловит G5).
- `demo/insecure/make_model_fixtures.py` — генерит `.pkl` (G4 блок) и `.safetensors` (G4 PASS).
- `demo/model_card_complete.json`, `demo/requirements_clean.txt` — «чистые» эталоны (должны PASS).

### 2.5 CI/CD — конвейер (`.github/workflows/`)
Три пайплайна на GitHub Actions (исполняются локально через self-hosted runner):

- **`ci.yml`** — на каждый PR. Джобы: `syntax` (компиляция), `data-gate`, `code-gate`,
  `dependency-gate`, `model-gate`, `registry-gate`, `db-smoke`, `build-gates`. Каждая гейт-джоба
  устроена по принципу **«чистое проходит / плохое блокируется»** (две проверки).
- **`train.yml`** — обучение в CI: **сначала G2** (нельзя обучать на грязном коде) → **диспатч по
  имени модели** на нужный train-скрипт → **G4** на полученном артефакте → consistency-тест →
  регистрация (alias=`candidate`).
- **`deploy.yml`** — выкатка в прод: проверка HITL (для HIGH ждёт Approve) → метаданные из реестра
  → G2 → сборка образа → **trivy** → **G4 (сверка SHA)** → **cosign подпись** → проверка подписи →
  копия в прод-хранилище (WORM/неизменяемо) → **повторная сверка SHA перед `docker run`** →
  health-check → переключение alias=`production`.

## Часть 3. Работа разработчика C — модели, рантайм, мониторинг, UI

### 3.1 Три ML-модели (разные по типу)

| # | Модель | Тип | Артефакт | Сервис/порт |
|---|---|---|---|---|
| 1 | `credit_scoring` | LogReg, табличная | `.onnx` | `src/serve/app.py` :8080 `/predict` |
| 2 | `text_classifier` | TF-IDF + LogReg, текст | `.onnx` | `src/serve/app_text.py` :8081 `/classify` |
| 3 | `transaction_risk` | GBT, табличная (6 фич) | `.onnx` | `src/serve/app_risk.py` :8082 `/predict` |

Каждая обучается своим скриптом (`src/train/train.py`, `train_text.py`, `train_risk.py`).
**Все сохраняются в ONNX** — это формат из «белого списка» G4 (НЕ pickle). Это не случайность:
так модель C автоматически проходит G4 модели B. Каждый train-скрипт пишет три файла, которых
ждёт `train.yml` от B:
- `artifacts/<модель>.onnx` — сам артефакт,
- `artifacts/model_path.txt` — путь к нему,
- `artifacts/run_id.txt` — id запуска MLflow (если поднят).

### 3.2 Единая фичеинженерия — `src/common/features.py` (ключевое решение)

«Фичи» — это как сырые поля (`amount`, `age`, текст) превращаются в числа для модели.
Проблема индустрии (#19 Training-Serving Skew): если при **обучении** фичи считаются одной
формулой, а при **инференсе** — другой, модель в проде тихо врёт. Решение C: **одна функция на
обоих концах**:
- `featurize_row(amount, age)` — модель №1,
- `featurize_text(text)` — модель №2,
- `featurize_risk_row(amount, age)` — модель №3.

И `train_*.py`, и `serve/app_*.py` **импортируют ровно эти функции**. Чтобы никто случайно не
сделал «свою копию» в сервисе, есть тест (см. 3.5), который падает при расхождении.

### 3.3 G7 — защита прод-API в реальном времени (`src/serve/app_*.py`)

Каждый инференс-сервис — это FastAPI с защитным слоем (middleware). Что он делает с запросом:
- **Rate limit → 429:** считает запросы по ключу/IP в Redis; больше лимита в минуту → отдаёт
  `429 Too Many Requests`. Защита от кражи модели перебором (#5) и DoS (#6). *Если Redis не
  поднят — есть запасной счётчик в памяти.*
- **Валидация входа → 422:** строгая схема (Pydantic). `amount` должен быть > 0, `age` 0..120,
  текст не длиннее лимита. Мусор отбивается `422` ещё до модели (#11 evasion, #6).
- **Лимит размера тела → 413:** гигантский запрос обрезается (#6 DoS).
- **Output reduction:** наружу отдаётся **решение** (`{"decision":"approve"}`), а не сырая
  вероятность `0.8123`. Это мешает «скопировать» модель и понять, был ли человек в обучении
  (#5, #13).
- **DLP в логах:** перед записью в лог номера карт и email **маскируются** (`a***@b.com`) (#12).

Скрипт **`src/serve/attack_sim.py`** эмулирует атаку: шлёт 200 параллельных запросов — и видно,
как сервис начинает массово отвечать `429`. Это и есть «живое» доказательство G7 на демо.

### 3.4 G6 — мониторинг прода 24/7 (`src/monitor/monitor.py`)

Работает **постоянно**, а не по кнопке. Две задачи:
- **Дрейф данных (PSI):** сравнивает распределение прод-трафика с обучающим. Метрика **PSI**
  (Population Stability Index): `>0.25` — значимый сдвиг → алерт `DRIFT DETECTED`. Реализован
  свой расчёт по корзинам (работает без внешних библиотек) + опциональный `evidently`. Может брать
  трафик из файла (`--current`) или **из живых логов инференса** (`--live-model`, см. 3.6).
- **Подмена модели (#4):** периодически пересчитывает SHA-256 запущенного артефакта и сверяет с
  реестром. Не совпало → `🚨 ПОДМЕНА МОДЕЛИ`.

Режим сервиса: `--watch 30` — повторять каждые 30 секунд. При тревоге пишет событие в Audit Trail.

### 3.5 Тест парности обучение↔инференс — `tests/test_consistency.py` (#19)

21 тест на все 3 модели. Главные:
- **feature parity** — фичи из train-пути и serve-пути идентичны на наборе примеров.
- **serve uses common source** — проверка, что `serve.featurize_* is common.featurize_*`
  (буквально один и тот же объект). Если кто-то форкнет логику в сервисе — тест упадёт.
- проверка стабильности предсказаний модели (если артефакт и onnxruntime доступны).

Этот тест **B встроил в `train.yml`** — то есть обучение в CI не пройдёт, если train и serve
разошлись. Хороший пример стыковки B↔C.

### 3.6 Audit Trail без бэкенда A — `src/common/audit.py` (решение по graceful-деградации)

Пока A не сделал базу, runtime-слой всё равно должен оставлять след. `audit.py`:
- `log_event(...)` — **сначала пробует** `core.db.log_event` (когда A готов) → **иначе** пишет в
  `logs/events.jsonl`. Когда A появится — переключение автоматическое, код менять не надо.
- `log_feature(model, {...})` — пишет фичи запроса (с DLP-маскированием) в
  `logs/inference_<model>.jsonl`. Это и есть «корм» для PSI-мониторинга (3.4).

То есть serve пишет фичи → monitor их читает и считает дрейф **на живом трафике**, всё без A.

### 3.7 Веб-интерфейс — `ui/app.py` (Streamlit)

9 вкладок, единый процесс (не россыпь кнопок). Пока A не отдаёт реальные данные, UI работает на
**моках** с автоматическим переключением на API (`_api_get → mock`). Вкладки:

1. **Кабинет/Верификация** — форма (модель, Run ID, Git SHA) + наглядный прогресс по гейтам.
2. **Паспорт модели** — owner, **Tier-бейдж** (🔴 HIGH / 🟡 MED / 🟢 LOW), lineage (данные↔код↔модель),
   связанные находки, история.
3. **Реестр** — список моделей/датасетов, фильтры по статусу/Tier/owner.
4. **История событий** — Audit Trail + кнопка **«проверить цепочку хешей»** (целостность лога #24).
5. **Находки** — все сработки; «Показать причину» (JSON-evidence), «Отметить False Positive»,
   «Перезапустить», и **маппинг находка→угроза**.
6. **Инструменты/Сканеры** — что делает каждый инструмент (gitleaks, bandit, pip-audit, trivy,
   modelscan, cosign, evidently) и к какой угрозе он привязан.
7. **Деплой/Approve** — **HITL** для Tier=HIGH; **RBAC**: под ролью DS кнопка Approve даёт `403`.
8. **Доступы (админка)** — регистрация пользователей, роли, доступ к датасетам (для MLSecOps).
9. **Дашборд** — дрейф (PSI), статистика 429, pass-rate гейтов; режим CEO read-only.

В сайдбаре при `APP_DEBUG=true` — **переключатель ролей DS/MLSecOps** (только для демо; в проде
роль берётся из аутентификации).

## Часть 4. Как всё взаимодействует (стыки и потоки)

### 4.1 Поток артефакта сквозь гейты
```
1. Данные загрузили → G1 (B). PASS → можно обучать. FAIL → карантин + находка.
2. Код в git → G2 (B: секреты/SAST/CVE) + G3 (B: имена/версии/источник).
3. Обучение в CI (C: train_*.py) → артефакт .onnx (формат, который примет G4).
4. Артефакт → G4 (B: формат/скан/SHA/подпись).
5. Перед записью в реестр → G5 (B: паспорт + lineage + Tier).
6. Деплой: HITL для HIGH → подпись → прод. Прод-API защищён G7 (C).
7. В проде постоянно работает G6 (C): дрейф + подмена.
```

### 4.2 Три «контракта», на которых всё держится
1. **Контракт гейта** (B): JSON + exit 0/1. Благодаря ему оркестратор (A) и CI вызывают любой
   гейт одинаково и кладут `evidence` в находки → UI показывает причину.
2. **Контракт обучения** (стык B↔C): `train_*.py` пишут `model_path.txt`/`run_id.txt`, артефакт в
   ONNX. `train.yml` (B) это читает и гонит G4.
3. **Единая фичеинженерия** (C) + **consistency-тест** (C), встроенный в `train.yml` (B) — гарантия
   #19. Это место, где B и C «сшиты» тестом.

### 4.3 Граница с разработчиком A (что на заглушках)
Всё, что требует базы/реестра/центрального бэкенда — пока на **фолбэке**, но уже подготовлено:
- запись истории → `logs/events.jsonl` (вместо Postgres) через `audit.log_event`;
- фичи для мониторинга → `logs/inference_*.jsonl` (вместо БД);
- UI → моки (вместо `/api/v1/...`);
- `train.yml`/`deploy.yml` → `curl` к будущим ручкам A с `|| WARNING` (не падают).

Когда A реализует свой слой, всё **переключится автоматически** — точки интеграции уже на месте.

### 4.4 Диаграмма взаимодействия (упрощённо)
```
        ┌─────────── B: гейты (свои Docker-образы) ───────────┐
данные ─►│ G1 │  код ─►│ G2 │ G3 │   .onnx ─►│ G4 │  паспорт ─►│ G5 │
        └──┬─────────────┬──────────────────────┬──────────────┬──┘
           │ JSON+exit    │ (CI: train.yml, deploy.yml)         │
           ▼              ▼                                      ▼
        находки/evidence  ──────►  оркестратор A (пока фолбэк logs/*.jsonl)  ──► UI (C)
                                                                                    ▲
        ┌──────────── C: рантайм/мониторинг ─────────────┐                          │
        │ serve (G7): 429/422/DLP/output-reduction       │── фичи → logs ──► monitor│(G6)
        │ 3 модели, фичи через common/features (#19)      │                          │
        └────────────────────────────────────────────────┘──────────────────────────┘
```

## Часть 5. Что умеет платформа прямо сейчас (возможности)

Можно вживую (см. [`19_LOCAL_DEV_WITHOUT_A.md`](19_LOCAL_DEV_WITHOUT_A.md), команды `make ...`):
- Загрузить датасет и увидеть **блок отравленного/с ПДн** (G1).
- Поймать **секрет в коде, CVE, опасный `shell=True`** (G2).
- Поймать **поддельный пакет `pytirch`** (G3).
- Заблокировать **`.pkl`-модель** и поймать **подмену по SHA** (G4).
- Заблокировать **модель без паспорта/lineage** и проверить **правила Tier** (G5).
- Обучить **3 разные модели** в безопасном формате (ONNX).
- Поднять **прод-API** и увидеть, как атака упирается в **429**, мусор — в **422**, а ПДн в логах
  **замаскированы** (G7).
- Запустить **мониторинг**: `DRIFT DETECTED` по PSI и `ПОДМЕНА МОДЕЛИ` по SHA (G6).
- Проверить, что **обучение и инференс считают фичи одинаково** (#19, 21 тест).
- Посмотреть всё в **вебе**: реестр, история, находки с причиной, Tier, HITL, RBAC-403, дашборд.

Запуск всего одним прогоном: `make setup && make demo`.

## Часть 6. Технические решения и почему так (резюме)

| Решение | Почему |
|---|---|
| Один контракт гейта (JSON+exit) | любой гейт запускается одинаково везде; легко добавлять новые |
| Гейт не пишет в БД | работает в CI без базы; запись — забота оркестратора |
| Один гейт = один Docker-образ | изоляция опасных артефактов, чистые версии инструментов |
| Модели только в ONNX | автоматически проходят G4 (анти-pickle-RCE) |
| Единая `features.py` + consistency-тест | устраняет training-serving skew (#19) гарантированно |
| Output reduction + rate-limit + DLP | защита модели и данных в рантайме без переобучения |
| `audit.py` с фолбэком в JSONL | runtime-слой работает и оставляет след до готовности A |
| Tier по авто-правилам (внешнее→HIGH) | «подозревай худшее»; критичное не уедет в прод без HITL |
| Графовая деградация (SKIP, fallback) | демо и разработка не ломаются из-за отсутствия инструмента |

## Часть 8. Что ещё не сделано (честно)
- **Зависит от A:** реальная БД (история/реестр), хранилище WORM, авторизация, центральная ручка
  `/verify`, регистрация моделей. Сейчас — фолбэки/моки.

  пока с мягкой деградацией.
- **cosign-ключи** для подписи на деплое заводит инфраструктура/A (код шагов готов).

Когда A закроет своё — платформа станет полностью интегрированной без переписывания B и C.
